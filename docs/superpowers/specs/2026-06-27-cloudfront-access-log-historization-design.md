# CloudFront Access-Log Historization — Design

**Date:** 2026-06-27
**Status:** Approved (design)
**Scope:** `packages/infrastructure` only. No application/Astro/CMS-frontend changes.

> **Amendment (later):** delivery was switched from flat to Hive-partitioned.
> Each pipeline now carries an `s3_delivery_configuration` block with
> `suffix_path = "{yyyy}/{MM}/{dd}"` and `enable_hive_compatible_path = true`,
> so objects land at `raw/site/year=YYYY/month=MM/day=DD/` and
> `raw/cms/year=YYYY/month=MM/day=DD/`. The per-distribution prefixes
> (`raw/site/` + `raw/cms/`) are unchanged. All "flat under each prefix" / "no
> Hive partitioning" / "no `s3_delivery_configuration` block" statements below
> are superseded. `enable_hive_compatible_path` MUST be true: only then does AWS
> allow the key=value layout and auto-expand the bare `{yyyy}/{MM}/{dd}`
> placeholders into `year=/month=/day=` (writing `year={yyyy}` literally while
> the flag is off is rejected with "Provided suffixPath is invalid").

## Goal

Capture the client IP and request metadata of every request to both CloudFront
distributions — `brigitte-le-roux.com` (public site) and
`cms.brigitte-le-roux.com` (Sveltia admin) — and retain it for 90 days in S3.
**Observe-only** — no blocking (WAF is out of scope; can be added independently
later). Just deliver the data to a bucket; no query layer or dashboard is built
or documented now (the Parquet data remains queryable later if ever wanted, but
that is out of scope).

Priorities, in order: (1) security / abuse investigation, (2) analytics /
curiosity. No user attribution — IP-level historization is sufficient.

## Why CloudFront access logs

CloudFront fronts everything: the `site` distribution serves the public Astro
site, the `cms` distribution serves the Sveltia SPA (`/cms/*` → S3) and the
github-gateway API (`/api/*` → API Gateway). Each distribution sees the real
viewer IP before any origin, so a log stream per distribution covers all paths
with zero application code changes. Logging the CMS distribution additionally
captures admin/login access attempts — useful for spotting unauthorized access.

## Decisions made during brainstorming

| Decision | Choice | Rationale |
|---|---|---|
| Act vs observe | **Observe only** | WAF (~$6/mo floor) deferred; additive later, no rework |
| Distributions logged | **Both `site` and `cms`** | CMS is auth-gated but logging it captures unauthorized-access attempts; the public site is where scanning happens |
| Bucket topology | **One shared bucket, two prefixes** | S3 has no per-bucket fee; one bucket with `raw/site/` + `raw/cms/` keeps both streams separable while the lifecycle rule prunes everything uniformly |
| Query layer | **None now — just deliver to S3** | Athena/dashboards are additive later; intentionally not built or documented now |
| Format | **Parquet** | Columnar; keeps future query/dashboard options cheap. Small CloudWatch conversion charge, negligible at this volume |
| S3 layout | **`raw/site/` and `raw/cms/`** | Per-distribution prefix; the `cs(Host)` field also distinguishes them but distinct prefixes make inspection/querying trivial at zero cost. Specifying the prefix in the destination ARN also suppresses CloudFront's default `AWSLogs/.../CloudFront/` path |
| Retention | **90 days, auto-delete** | S3 lifecycle rule; bucket self-prunes |
| Bucket name | **`brigitte-le-roux-website-cloudfront-logs-<account-id>`** | Account-id suffix per global CLAUDE.md guidance; dedicated to logs, separate from the `brigitte-le-roux-website` content bucket |
| Logging version | **Standard logging v2** | Keeps S3 ACLs disabled (AWS-recommended, bucket-policy based); supports Parquet output and a custom flat prefix |

## Architecture

```
brigitte-le-roux.com         →  aws_cloudfront_distribution.site ─┐
cms.brigitte-le-roux.com     →  aws_cloudfront_distribution.cms  ─┤
                                                                  │
                          standard logging v2 (CloudWatch Logs Delivery API,
                                  registered in us-east-1)
                                                                  │
                                                                  ▼
        ┌──────────────────────────────────────────────────────────┐
        │  delivery_source (site) ──► delivery ──► destination (S3)  │
        │  delivery_source (cms)  ──► delivery ──► destination (S3)  │
        └──────────────────────────────────────────────────────────┘
                                                                  │
                                                                  ▼
   S3: brigitte-le-roux-website-cloudfront-logs-<account-id> (eu-central-1)
        ├── raw/site/<auto-generated>.parquet
        └── raw/cms/<auto-generated>.parquet
                                                                  │
                                  (90-day lifecycle expiration, whole bucket)
```

The leaf filename (`<auto-generated>.parquet`) is produced by AWS's vended-log
delivery service (timestamp + unique id); it is not controllable, and many files
are written per period. We control only the `raw/site/` and `raw/cms/` folder
prefixes.

## Components

### 1. S3 log bucket — `s3.tf`, default eu-central-1 provider

One shared bucket, `brigitte-le-roux-website-cloudfront-logs-<account-id>`:

- `aws_s3_bucket`, `force_destroy = true`.
- `aws_s3_bucket_public_access_block` — all four flags `true`. (Unlike the
  content bucket, this is a pure log sink — no Sveltia `public-read` ACL
  accommodation needed.)
- `aws_s3_bucket_server_side_encryption_configuration` — `AES256` (SSE-S3).
  (v2 delivery to S3 supports SSE-S3; SSE-KMS would require extra key-policy
  grants — out of scope.)
- `aws_s3_bucket_lifecycle_configuration` — one rule, `Enabled`, **whole bucket**
  (`filter {}`, no prefix), `expiration { days = 90 }`, plus
  `abort_incomplete_multipart_upload { days_after_initiation = 3 }`. The bucket
  is dedicated to these logs (everything lives under `raw/`), so expiring
  everything is correct and simplest.
- `aws_s3_bucket_policy` — grant the log-delivery service principal write access
  (matches AWS's documented `AWSLogsDeliveryWrite` statement):
  ```
  Principal: { Service: "delivery.logs.amazonaws.com" }
  Action:    "s3:PutObject"
  Resource:  "<bucket-arn>/*"            # whole bucket — avoids path-prefix mismatch
  Condition:
    StringEquals:
      "s3:x-amz-acl":      "bucket-owner-full-control"
      "aws:SourceAccount": <this account id>
    ArnLike:
      "aws:SourceArn": "arn:aws:logs:us-east-1:<account>:delivery-source:*"
  ```
  One statement with the `delivery-source:*` wildcard `SourceArn` covers both
  delivery sources. Reuse the existing `data.aws_caller_identity.current`
  (declared in `iam.tf`) for the account id.

  **Gotcha (known failure mode):** if the `aws:SourceAccount` / `aws:SourceArn` /
  `s3:x-amz-acl` conditions are missing or wrong, or the `Resource` path doesn't
  cover where logs land, delivery **silently fails** with `AccessDenied` — logs
  never appear and nothing is surfaced on the distribution. Whole-bucket
  `Resource` sidesteps the prefix-mismatch trap AWS documents.

### 2. Log delivery (v2) — `logs.tf`, all six resources use `provider = aws.us_east_1`

The CloudWatch Logs Delivery API for CloudFront must be called in `us-east-1`
even though the destination bucket is in `eu-central-1` (cross-region delivery
is allowed). The `aws.us_east_1` alias already exists in `main.tf` (used for the
ACM certs).

> **Naming note:** these resources are prefixed `aws_cloudwatch_log_delivery_*`
> even though the source is CloudFront and the destination is S3 (CloudWatch
> stores nothing here). "Log delivery" is a generic CloudWatch Logs subsystem
> that routes logs from many AWS sources to S3/Firehose/CloudWatch/X-Ray;
> CloudFront's docs call this same feature "standard logging v2." The
> `cloudwatch` prefix is just the API family that operates the pipe — logs land
> as Parquet in S3, not in CloudWatch.

Two parallel pipelines (one per distribution), each three resources:

| Resource | Site | CMS |
|---|---|---|
| `aws_cloudwatch_log_delivery_source` | `site` — `log_type = "ACCESS_LOGS"`, `resource_arn = aws_cloudfront_distribution.site.arn` | `cms` — `resource_arn = aws_cloudfront_distribution.cms.arn` |
| `aws_cloudwatch_log_delivery_destination` | `site` — `output_format = "parquet"`, `delivery_destination_configuration { destination_resource_arn = "<bucket-arn>/raw/site" }` (the destination *type* is computed from the ARN — not an input) | `cms` — same with `<bucket-arn>/raw/cms` |
| `aws_cloudwatch_log_delivery` | links `site` source → `site` destination, `record_fields` = 14-field set (§3) | links `cms` source → `cms` destination, same `record_fields` |

- The `/raw/site` and `/raw/cms` prefixes in each destination ARN suppress
  CloudFront's default `AWSLogs/aws-account-id=<id>/CloudFront/` path; logs land
  flat under the respective prefix.
- **No `s3_delivery_configuration` block** on either delivery — flat delivery
  under the prefix, no Hive partitioning, no `suffix_path` (this is what makes
  the layout flat and removes any suffix-variable ambiguity).

### 3. Record fields (the data we actually keep) — 14-field set

```
date, time, c-ip, c-country, asn,
cs-method, cs-protocol, cs(Host), cs-uri-stem, cs-uri-query,
sc-status, x-edge-result-type, x-edge-location, cs(User-Agent)
```

`c-ip` is the whole point (client IP). The rest give enough context to tell a
scanner from a real visitor and to group by path/status. `cs(Host)` also
distinguishes site vs CMS traffic within either stream. The full CloudFront v2
field list is available if more is wanted later — adding fields is a one-line
change.

**Exact field names matter** — they are validated at apply time. `date`/`time`
(there is no single `timestamp` standard field); Host and User-Agent use the W3C
parenthesized form `cs(Host)` / `cs(User-Agent)`; the rest are hyphenated
lowercase.

**Geo note:** standard logging **v2** can select a subset of real-time fields, so
geography is available natively per row — no header injection, no IP lookup:
- **`c-country`** — ISO 3166-1 alpha-2 country code, derived by CloudFront from
  the viewer IP (e.g. `FR`, `US`).
- **`asn`** — viewer's Autonomous System Number (ISP / network owner);
  distinguishes datacenter/VPN/hosting traffic from residential — a strong
  bot/scanner signal.
- `x-edge-location` — serving POP (e.g. `FRA56`); rough-region hint.

Precise *city* still needs an IP→geo lookup later, but country + network are
columns in the logs.

## Data flow

1. Viewer hits `brigitte-le-roux.com` or `cms.brigitte-le-roux.com`; the
   respective CloudFront distribution records the request (real `c-ip`).
2. Standard logging v2 batches and delivers Parquet files flat to
   `s3://…-cloudfront-logs-<account-id>/raw/site/` or `/raw/cms/`
   (delivery latency: minutes, not real-time).
3. Lifecycle rule deletes objects 90 days after creation.

## Error handling / operational notes

- **Silent delivery failure** is the main risk — verify after `apply` that
  Parquet objects actually appear under both `raw/site/` and `raw/cms/` within
  ~15 min of generating traffic. If empty, the bucket policy
  conditions/`Resource` are the first suspect.
- **Cost:** pennies/year at this site's volume. S3 storage of a few MB/month of
  Parquet, plus a small CloudWatch *conversion* charge for the Parquet output
  (negligible here).
- **Teardown:** `force_destroy = true` lets `terraform destroy` remove the
  bucket with objects present.

## Out of scope

- AWS WAF / blocking / rate limiting (additive later; ~$6/mo floor).
- User-to-IP attribution.
- Any query layer or dashboard (Athena, QuickSight, Grafana, custom page) — the
  Parquet data remains queryable later if wanted, but nothing is built or
  documented now.
- Date/Hive partitioning of the S3 path (deliberately flat under each prefix).
- Logging the API Gateway origin directly (CloudFront already captures `/api/*`
  on the `cms` distribution at the edge).
